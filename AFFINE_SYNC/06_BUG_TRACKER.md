# Bug Tracker

## BUG-001
| Field | Value |
|---|---|
| Module | Auto Layout / Build AI Draft |
| Description | Hero photo renders in an incorrect position (and, on further investigation, sometimes as the wrong photo entirely) on multi-page drafts generated by `buildAIDraft()` |
| Severity | High — affects core Auto Layout workflow output |
| Status | **FIXED** — verified via live browser test |
| Reproduction steps | 1. Upload multiple photos (10+ recommended, so overflow spans two content pages). 2. Let Hero Analysis produce a recommendation. 3. Click "Build AI Draft" to generate a multi-page project. 4. Navigate to page 3. 5. Hero photo position/identity did not match the page's intended photo/frame. |
| Root cause | Two compounding defects in `buildAIDraft()` → `renderComposition()` → `serializeActivePage()` (all in OCF_START.html): **(1) Geometry timing race** — `clearSlot('heroLayer')` reset `hero.{x,y,w,h}` to the `{0,0,420,522}` default on every `renderComposition()` call; the real cover-fit was only ever computed asynchronously inside `heroImg.onload`, which never fires within `buildAIDraft()`'s fully-synchronous page loop, so `serializeActivePage()` always captured the stale default instead of the true fit. **(2) Wrong hero identity** — `serializeActivePage()` reads `heroPhotoId` from the global `heroIndex`, which was only set once (via `setHero()`) before the loop started and never updated per page, so every generated page recorded the same `heroPhotoId` (the original recommended hero) regardless of which photo the layout plan actually assigned. This matches diagnostic categories (2)/(3) from the original four-way split — confirmed. |
| Fix commit | `3decadb5ddd5f0929bb80479b808aafadc8d78e1` |
| Retest result | PASS — see `AFFINE_SYNC/05_TEST_RESULTS.md` |

## BUG-002
| Field | Value |
|---|---|
| Module | Whole automation pipeline: text extraction, photo distribution, multi-page generation, captions, editor controls |
| Description | A live real-user test found the automation-first workflow (locked core requirement, not an optional feature — see `03_APPROVED_DECISIONS.md`) largely missing, plus several editor controls appearing non-functional |
| Severity | Critical — product not accepted as a manual photo editor; automation pipeline is the required product |
| Status | **FIXED** — full one-click acceptance flow verified live |
| Reproduction / initial findings | Real-browser audit (not code inspection alone) found: (1) automatic Date/Time/Location/Department/Activity/Result/Public Information/Closing extraction did not exist at all; (2) automatic Facebook/TikTok caption generation did not exist; (3) multi-page generation was generic photo-count chunking, not content-section-driven (Cover/Activity/Results/Public Information/Closing); (4) "Export All Pages" did not exist; (5) `deletePage()`'s native `confirm()` dialog blocked browser-automation sessions (real users see a normal browser dialog — not a functional defect, but confusable with a frozen page); (6) two further defects surfaced once per-page text was implemented: `updateText()` used `.textContent=`, deleting the title/subtitle layers' resize/rotate handle elements on every edit; `clearSlot('heroLayer')` never reset `heroIndex`, so hero-less pages (Public Information/Closing) inherited the previous page's hero identity — the exact scenario an existing code TODO had flagged as unreached. |
| Root cause | Items 1–4 above: the locked automation-pipeline requirements had never been implemented in `OCF_START.html` (confirmed absent by full-file grep before implementation) — not a regression, a build gap. Items 6: `updateText`/`clearSlot('heroLayer')` were written for the earlier single-title, always-has-a-hero flow and never updated when per-page text/no-hero pages became reachable. |
| Fix commit | `57abfdc93de054cf9ad87690bd3b17c3fb6584c5` |
| Retest result | PASS — full flow (Upload Photos → Paste Event Text → Build AI Draft → automatic extraction/hero/distribution/pages/captions → edit → Save/Reopen → Export Current Page → Export All Pages) verified live with real uploaded photos and real event text. Detailed per-step table in `05_TEST_RESULTS.md`. |
